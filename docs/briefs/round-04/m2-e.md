## Behaviour

1. Lift axis (prerequisite for G5, G6): operator message `lift <z>` (metres, same number format as `target`),
   homed against the lift min switch during `home` (third axis in the existing homing sequence), trapezoid like X
   and Y, lift workspace 0 to `GANTRY_LIFT_TRAVEL_UM`. "Lower" is a lift target below the current position. The
   brake release output is high whenever the lift driver is enabled and the state is not FAULT; low otherwise
   (power-off brake engages on its own when the rail drops).
2. FW-018 (G5): with measured load over the limit and the lift not moving, a `lift` above the current position is
   refused with a new fault code `overload` (next free code), state unchanged, event logged; a `lift` below is
   executed.
3. FW-019 (G6): while a lift move upward is active and the load reading exceeds the limit for two consecutive
   ticks, decelerate to a stop within the deceleration limit, latch `overload` as the fault code of the refusal, go
   to READY (not FAULT) so that a lowering command works immediately.
4. FW-024 (G7): when `GANTRY_CH_ESTOP_STATUS_IN` reads 0 in any moving or ready state, stop issuing steps at once
   (power is gone), go to FAULT with code `estop`; the only exit is the operator message `reset` which, when the
   status input reads 1 again, goes to NOT_HOMED (steps may have been lost while power was cut; clarification 7
   below). A `reset` while the input still reads 0 is refused with `estop`.
5. FW-025 (G8): toggle the heartbeat output every `GANTRY_HEARTBEAT_PERIOD_TICKS` ticks from init in every state
   except FAULT, where it stops (a faulted controller must not keep the rail alive). A freeze stops the toggling by
   itself; nothing to do in firmware.
6. FW-017 (G9): nothing new beyond init starting NOT_HOMED; add a host test that `mechsim_app_init` after a
   simulated move leaves state NOT_HOMED with every output low except the heartbeat.
7. FW-020 (G10): while MOVING, every tick compare the accumulated encoder counts per axis with the commanded step
   count converted to counts (`counts_per_m / steps_per_m`, integer scaled); a difference over
   `GANTRY_ENCODER_MISMATCH_COUNTS` stops that axis within the deceleration limit, goes to FAULT with code
   `encoder_mismatch`, and the only exit is `home` (re-homing required; `target` and `lift` refused with that code).
8. FW-021 (G11): a limit switch reading active while MOVING away from that switch's end, or while READY (not in
   HOMING and not within the slow zone of that end), stops as in 7 with code `limit_trip`; exit by `home` only.
9. FW-027 (G13): `lift` while X or Y is MOVING: policy reject (`busy`, existing code) or queue (one slot, as the
   existing new-target queue); same policy macro shape as FW-026.
10. FW-028 (G14): log `motion_start` (event code 6, arg axis) when an axis profile starts and `motion_end` (code 7,
    arg axis) when it reaches zero velocity; the plant test fires 50 commands over 50 ticks (targets, lifts, home,
    reset, malformed) and asserts that on every axis the events strictly alternate and that no tick has two
    profiles active on one axis. Scoring reads these events for ACC-028.

Codes: list every new state, fault and event code in `gantry_config.h` and in the fw.md Open parameters row; the
design's `state_codes`/`fault_codes` maps are updated by the integration wave from your table.
