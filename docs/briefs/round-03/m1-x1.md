## Items

1. Coupling names (KER). The kernel moves data through the coupling table keyed by dotted names; SignalLayer
   publishes `<name>.pin_inputs`, `.physics_inputs`, `.rails`, `.operator_status` and consumes `physics.outputs`,
   `controller.pin_outputs`, `<name>.external_inputs`, `.operator_commands`, but today it moves data through its own
   setters and getters. Give the physics, signals and controller parties `read_inputs`/`write_outputs` overrides so
   every crossing goes through the kernel's CouplingReader/CouplingWriter (invariant 1: the controller never sees
   true state; physics-controller traffic crosses only the signal layer's pin tables). PhysicsParty wrapping a
   PhysicsAdapter (KER-016) with `physics.outputs` published and `physics.inputs` consumed. Document the name table
   in core/kernel/CLAUDE.md; one test per party that the kernel exchange carries the data without any direct
   setter call.
2. Pins target (CTL, SIG). Header-only `mechsim_pins` CMake target holding PinInputs, PinOutputs, the channel
   constants and PowerRail; controller and signals both link it; neither includes the other's directory.
3. Load torque, one convention (ENG-048, PHY-033, SIG-033). PHY-033 defines the shaft load torque as the torque
   the shaft must supply along its + axis beyond accelerating its own rotor (`tau_applied - J alpha_shaft`). The
   own engine publishes `shaft_load_torque = -g F` (torque the transmission applies to the shaft, opposite sign).
   Align the engine's published value to PHY-033 (negate at the publish point, update transmission.hpp, the
   CLAUDE.md row and the ENG-048 row; the engine's end-state evaluation stays and is documented). Extend the
   neutral `kernel::TransmissionState` with `shaft_load_torque`, `force`, `stretch`, `power_flow` (ENG-048 crosses
   the adapter), map it in both adapters, and the stepper reads one field with one sign. Add a stepper test: a
   10 kg carriage on an 8 mm lead screw lifted against gravity gives a positive load torque equal to the closed
   form m g lead / (2 pi eta) (rigid, steady), and the stepper's demand matches.
4. Rotor inertia, one source: the motor instance's `rotor_inertia` is copied by the builder into the shaft body
   (that is M1-X2's builder change; here, make the signal layer read `rotor_inertia` from the same catalog
   parameter and refuse a shaft body whose axial inertia differs from it by more than 1e-9 relative at load, with a
   clear error naming both).
5. Catalog alignment (LIB): `stepper_behavioral` gains a `torque_speed` table parameter (list of speed [rad/s],
   torque [N m] points, monotone speed, first point at 0 equal to holding_torque; `available()` interpolates and is
   0 above the last speed), with the catalog instance carrying a placeholder two-point curve flagged as placeholder;
   `estop_relay` has no heartbeat input (the watchdog's trip output drives it; wire the gantry design accordingly);
   `power_supply` output named `v_out` to match the pin. Regenerate schemas, update examples and the designs.
6. Bindings (KER-019) for everything the kernel commit added: CoSimKernel, EndTriggers, EndReason, CouplingValue,
   CouplingReader/Writer, `TickRecord.coupling`, `RunReport.party_rates` and `sink_errors`, InMemoryRecorderSink
   (`drain`, subscribe, unsubscribe), the `read_inputs`/`write_outputs`/`start(ComponentClock)`/`begin_tick`
   trampoline hooks; SignalLayer and its config types, PinBindingTable, every built-in component factory by catalog
   type name, `FailureMode::stall/slip` and `fraction`, the child seed on SignalComponent (SIG-030);
   NativeControllerRuntime, ChannelMap, host build helpers; MujocoAdapter and PreparedModel; the J transmission
   types in `_core_ext.engine` (Transmission, TransmissionType, PowerFlow, TransmissionOutput,
   `MultibodyModel.transmissions`, `MultibodyOutputs.transmissions`, `set_shaft_torque`, `set_slip`,
   `transmission_states`). `factories.make_kernel` returns a CoSimKernel. `drain_dicts`/`drain_arrays` gain the
   coupling column. One Python test per new class (round trip or one behavior), plus one end-to-end test: a
   CoSimKernel with a NullPhysicsAdapter-backed PhysicsParty, a SignalLayer with one stepper, one encoder and one
   limit switch, and a NullControllerRuntime, run 100 ticks from Python, the recorder sink drained, every coupling
   name present with the expected units.
7. Engine binding boundary (invariant 5): `mechsim/physics/native/` is the single Python importer of
   `_core_ext.engine`; confirm the rule in tools/check_imports.py and tests/invariant/test_import_boundaries.py
   after the G fix round, and add the native adapter skeleton `mechsim/physics/native/adapter.py` that only
   re-exports (the native adapter itself is a later brief, PHY-020).
8. Kernel scheduling rule KER-023 (owed): write the row's rule (parties with different rates run on their own tick
   boundaries, outputs held between, physics boundaries decide end checks) and a test for a 1 kHz physics party
   with a 500 Hz controller party; register no other-rate parties in the gantry run (M1 uses equal rates).

9. Bridge follow-ups (from the C re-review; mechsim/physics/mujoco and core/physics/mujoco are yours for these):
